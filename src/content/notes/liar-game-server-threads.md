## 무엇을 만들었나

네트워크 프로그래밍 수업의 3인 팀 프로젝트로 만든 라이어 게임입니다. 최대 8명이 TCP 소켓으로 접속하고, 한 명(라이어)만 제시어를 모른 채 시작해 대화로 라이어를 찾아내면 시민이 이깁니다. 저는 서버 측 멀티스레드 처리와 게임 로직을 맡았습니다. `LiarServer`, 클라이언트별 수신 스레드 `OneClientModul`, 진행을 담당하는 `GameManager`가 제 몫입니다.

## 스레드를 세 종류로 나눈 이유

처음 만든 버전은 `ServerSocket`의 accept 루프와 게임 진행이 같은 스레드에 있었습니다. 게임이 시작돼 발언 타이머가 도는 동안 새 접속을 받을 수 없었고, 반대로 accept에서 블로킹되면 게임이 멈췄습니다. 그래서 역할별로 스레드를 나눴습니다.

- **serverThread**: `ServerSocket.accept()` 루프만 돕니다. 접속이 오면 `OneClientModul` 스레드를 하나 만들어 `Vector`에 보관합니다. 인원 상한(8명), 게임 중 입장 차단, 강퇴 처리도 여기서 합니다.
- **OneClientModul (접속당 1개)**: 클라이언트 한 명의 수신을 기다립니다. 메시지 접두사로 라이어의 제시어 추리(`liarTopic`), 투표(`cVote`), 게임 명령(`gm`), 그 외 채팅을 구분해 분기하고 전체에 브로드캐스트합니다.
- **gameThread**: 시작 버튼이 눌리면 `GameManager`를 구동합니다. 주제 풀(181개)에서 제시어를 뽑고, 라이어를 무작위로 정하고, 발언 순서를 섞어 1인당 10초씩 채팅 잠금을 풀었다 잠그고, 20초 투표를 집계해 승패를 판정합니다.

이렇게 나누자 게임 중에도 accept 루프는 살아 있어 입장 차단 메시지를 보낼 수 있었고, 전원이 투표를 마치면 `OneClientModul`이 `gameThread.interrupt()`를 호출해 20초를 기다리지 않고 바로 집계로 넘어갈 수 있었습니다.

## 디버깅에서 배운 것

가장 오래 붙든 버그는 강퇴와 브로드캐스트의 타이밍이었습니다. 강퇴된 클라이언트의 소켓을 닫는 순서와 `Vector`에서 제거하는 순서가 어긋나면, 브로드캐스트가 이미 닫힌 스트림에 쓰다가 예외를 내거나 반대로 나간 사람에게 메시지가 한 번 더 갔습니다. 스레드가 여러 개일 때는 "누가 먼저 실행되는가"를 코드 순서로 보장할 수 없다는 것을 손으로 겪었습니다. 프레임워크가 숨겨 주던 것을 직접 다뤄 본 것이 이 프로젝트에서 남은 가장 큰 부분입니다.

## 지금 다시 만든다면 바꿀 네 가지

코드를 다시 읽으며 고칠 점을 네 가지로 정리했습니다.

1. **텍스트 접두사 프로토콜은 확장에 취약합니다.** 메시지 종류가 늘 때마다 문자열 비교 분기가 늘어납니다. JSON 같은 구조화된 메시지와 명령 enum으로 바꾸겠습니다.
2. **동기화가 `Vector`에 기대고 있습니다.** 게임 진행 중 입퇴장이 겹치면 순회와 수정이 경합할 수 있습니다. 접속 목록을 `CopyOnWriteArrayList`나 명시적 잠금으로 보호해야 합니다.
3. **네트워크 스레드에서 Swing 컴포넌트를 직접 갱신했습니다.** UI 갱신은 `SwingUtilities.invokeLater`로 이벤트 디스패치 스레드에 위임했어야 합니다.
4. **리소스를 작업 디렉터리 상대 경로로 읽습니다.** JAR로 패키징하면 깨지므로 classpath 리소스로 옮겨야 합니다. `주제.txt`가 EUC-KR인데 플랫폼 기본 문자셋으로 읽는 것도 같은 부류의 문제입니다.

작은 프로젝트지만, 접속 처리와 진행 로직을 다른 스레드로 나누는 판단과 그 뒤에 남은 동기화 문제는 지금 플랫폼에서 배치 작업과 사용자 요청이 같은 데이터를 건드릴 때 보는 문제와 같은 모양입니다.
