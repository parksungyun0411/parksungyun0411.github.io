## 무엇을 만들었나

네트워크 프로그래밍 수업의 3인 팀 프로젝트로 만든 라이어 게임입니다. 최대 8명이 TCP 소켓으로 접속하고, 한 명(라이어)만 제시어를 모른 채 시작해 대화로 라이어를 찾아내면 시민이 이깁니다.

제 몫은 클라이언트 쪽이었습니다. 로그인 화면의 버튼 위치와 창 크기를 맞추고, EUC-KR로 깨져 있던 소스의 한글 문자열과 주석을 UTF-8로 옮기고, Gradle wrapper와 빌드 설정을 추가했습니다. 서버 코드(`LiarServer`, `OneClientModul`, `GameManager`)는 마지막 날 팀원 계정으로 한 번에 올라와 있어 개발 중 분담이 커밋에 남아 있지 않습니다. 그래서 아래의 서버 이야기는 제가 설계한 기록이 아니라, 졸업 뒤 팀 서버 코드를 다시 읽고 정리한 것입니다.

## 서버가 스레드를 세 종류로 나눈 방식

- **serverThread**: `ServerSocket.accept()` 루프만 돕니다. 접속이 오면 `OneClientModul` 스레드를 하나 만들어 `Vector`에 보관합니다. 인원 상한(8명), 게임 중 입장 차단, 강퇴 처리도 여기서 합니다.
- **OneClientModul (접속당 1개)**: 클라이언트 한 명의 수신을 기다립니다. 메시지 접두사로 라이어의 제시어 추리(`liarTopic`), 투표(`cVote`), 게임 명령(`gm`), 그 외 채팅을 구분해 분기하고 전체에 브로드캐스트합니다.
- **gameThread**: 시작 버튼이 눌리면 `GameManager`를 구동합니다. 주제 풀(181개)에서 제시어를 뽑고, 라이어를 무작위로 정하고, 발언 순서를 섞어 1인당 10초씩 채팅 잠금을 풀었다 잠그고, 20초 투표를 집계해 승패를 판정합니다.

이렇게 나뉘어 있어 게임 중에도 accept 루프가 살아 있고 입장 차단 메시지를 보낼 수 있습니다. 전원이 투표를 마치면 `OneClientModul`이 `gameThread.interrupt()`를 호출해 20초를 기다리지 않고 바로 집계로 넘어갑니다.

## 코드에서 찾은 경합 지점

스레드가 여러 개인 이 구조에서 가장 위험한 곳은 접속 목록입니다. 강퇴는 `Vector`를 순회하다 해당 접속을 지우고, 접속이 끊긴 클라이언트의 수신 스레드도 같은 목록에서 자기 자신을 지웁니다. 그 사이 다른 스레드가 같은 목록을 순회하며 브로드캐스트하면, 이미 닫힌 스트림에 쓰다가 예외가 나거나 순회 중 수정으로 예외가 날 수 있습니다. 스레드가 여러 개일 때는 "누가 먼저 실행되는가"를 코드 순서로 보장할 수 없다는 점이 이 목록 하나에서 그대로 드러납니다.

## 다시 만든다면 바꿀 다섯 가지

1. **브로드캐스트가 한 명 때문에 멈춥니다.** 접속자마다 차례로 블로킹 쓰기를 하므로 느린 접속자 하나가 전체 전송을 막습니다. 쓰기 하나가 실패하면 비어 있는 `catch`에서 루프가 끝나, 나머지 접속자에게도 메시지가 가지 않습니다. 접속자별 송신 큐로 나누고 실패한 접속만 정리하겠습니다.
2. **텍스트 접두사 프로토콜은 확장에 취약합니다.** 메시지 종류가 늘 때마다 문자열 비교 분기가 늘어납니다. JSON 같은 구조화된 메시지와 명령 enum으로 바꾸겠습니다.
3. **동기화가 `Vector`에 기대고 있습니다.** 위의 경합 지점이 여기서 나옵니다. 접속 목록을 `CopyOnWriteArrayList`나 명시적 잠금으로 보호해야 합니다.
4. **네트워크 스레드에서 Swing 컴포넌트를 직접 갱신했습니다.** UI 갱신은 `SwingUtilities.invokeLater`로 이벤트 디스패치 스레드에 위임했어야 합니다.
5. **리소스를 작업 디렉터리 상대 경로로 읽습니다.** JAR로 패키징하면 깨지므로 classpath 리소스로 옮겨야 합니다. 소스의 한글은 제가 UTF-8로 옮겼지만, `주제.txt`는 여전히 EUC-KR인데 플랫폼 기본 문자셋으로 읽습니다. 인코딩을 코드에 적어 두지 않으면 실행 환경에 따라 제시어가 깨집니다.

작은 프로젝트지만, 접속 처리와 진행 로직을 다른 스레드로 나누는 구조와 그 뒤에 남은 동기화 문제는 지금 플랫폼에서 배치 작업과 사용자 요청이 같은 데이터를 건드릴 때 보는 문제와 같은 모양입니다.
